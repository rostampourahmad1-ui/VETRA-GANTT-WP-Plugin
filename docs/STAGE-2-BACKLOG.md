# بک‌لاگ آماده اجرای مرحله ۲ — تکمیل قابلیت‌های محصول

مبنای محدوده: [V1-SCOPE.md](V1-SCOPE.md)  
وضعیت: Ready  
ترتیب اجرا اجباری است، زیرا آیتم‌های بعدی به قراردادها و UI آیتم‌های قبلی وابسته‌اند.

## Definition of Ready

- محدوده و قواعد دامنه در `V1-SCOPE.md` تصویب شده است.
- محیط هدف WordPress تک‌سایتی و پایلوت محدود است.
- ساختار فعلی `projects`، `tasks` و `dependencies` مبنای migration خواهد بود.
- تغییرات مرحله ۲ نباید منابع، هزینه، baseline یا مسیر بحرانی را وارد محصول کنند.

## Epic 2.1 — زیرساخت مدیریت پیشخوان (P0)

### S2-01: ثبت منوی مدیریت

خروجی:

- منوی «وترا گانت» برای کاربران دارای `edit_posts`
- زیرصفحه فهرست پروژه‌ها
- enqueue شدن assetها فقط در صفحات افزونه

معیار پذیرش:

- مهمان و کاربر فاقد مجوز به صفحه دسترسی ندارند.
- مدیر همه پروژه‌ها و کاربر عادی فقط پروژه‌های خود را می‌بیند.

### S2-02: فهرست پروژه‌ها

خروجی:

- جدول عنوان، تاریخ شروع شمسی، تعداد فعالیت، مالک برای مدیر و عملیات
- حالت خالی، loading و error
- دکمه ایجاد پروژه و کپی shortcode

معیار پذیرش:

- داده cross-user در HTML یا API افشا نمی‌شود.
- shortcode صحیح با شناسه پروژه کپی می‌شود.

## Epic 2.2 — CRUD پروژه و تقویم (P0)

### S2-03: قرارداد REST پروژه

خروجی:

- `POST /projects`
- `PUT /projects/{id}`
- `DELETE /projects/{id}`
- اعتبارسنجی title، start_date، workdays و holidays
- حذف اتمیک پروژه، فعالیت‌ها و وابستگی‌ها

معیار پذیرش:

- تقویم بدون روز کاری رد می‌شود.
- تعطیلات تکراری normalize می‌شوند.
- حذف پروژه دیگران با 403 رد می‌شود.

### S2-04: فرم ایجاد و ویرایش پروژه

خروجی:

- ورود عنوان و تاریخ شروع شمسی
- انتخاب روزهای کاری
- افزودن/حذف تعطیلات شمسی
- جلوگیری از submit تکراری و هشدار تغییر ذخیره‌نشده

معیار پذیرش:

- خطای backend داخل فرم نمایش داده می‌شود.
- بازکردن مجدد فرم، داده ذخیره‌شده را دقیق نمایش می‌دهد.

### S2-05: حذف پروژه

خروجی:

- دیالوگ تأیید با عنوان پروژه و تعداد فعالیت‌ها
- حذف فقط پس از تأیید صریح

معیار پذیرش:

- لغو دیالوگ هیچ تغییری ایجاد نمی‌کند.
- پس از حذف هیچ task یا dependency یتیم باقی نمی‌ماند.

## Epic 2.3 — ساختار WBS (P0)

### S2-06: سرویس بازمرتب‌سازی

خروجی:

- endpoint اتمیک برای ترتیب مجموعه فعالیت‌ها
- normalize شدن `sort_order`
- جلوگیری از انتقال زیرمجموعه به داخل خودش

معیار پذیرش:

- ترتیب پس از reload ثابت می‌ماند.
- payload شامل فعالیت پروژه دیگر رد می‌شود.

### S2-07: کنترل بالا/پایین و تورفتگی

خروجی:

- کنترل‌های قابل استفاده با موس و صفحه‌کلید
- تورفتگی، بیرون‌رفتگی، انتقال بالا و پایین
- بازتولید خودکار WBS بعد از هر تغییر

معیار پذیرش:

- ساختار سه‌سطحی قابل ایجاد است.
- هیچ چرخه یا WBS تکراری تولید نمی‌شود.
- فیلد WBS دستی از فرم حذف می‌شود.

## Epic 2.4 — تکمیل تجربه ویرایش فعالیت (P1)

### S2-08: state فرم و ارسال امن

خروجی:

- disable شدن submit هنگام درخواست
- success/error اختصاصی داخل دیالوگ
- هشدار بستن فرم تغییرکرده
- بازنشانی state پس از بسته‌شدن

### S2-09: رفتار وابسته به نوع فعالیت

خروجی:

- milestone مدت صفر و پایان غیرقابل ویرایش
- حالت auto پایان را فقط‌خواندنی می‌کند
- summary دارای فرزند، تاریخ و مدت محاسباتی دارد

### S2-10: پیام‌های خطای عملیاتی

خروجی:

- پیام مشخص برای چرخه، والد نامعتبر، وابستگی تکراری و حذف سرگروه
- عدم جایگزینی داده سالم UI با پاسخ ناقص

## Epic 2.5 — خروجی و واکنش‌گرایی (P1)

### S2-11: خروجی CSV

خروجی:

- CSV دارای WBS، عنوان، نوع، مدت، شروع، پایان، پیش‌نیاز و سهم
- UTF-8 BOM و تاریخ شمسی برای مصرف کاربر
- کنترل دسترسی یکسان با مشاهده پروژه

### S2-12: موبایل و دسترس‌پذیری

خروجی:

- toolbar و دیالوگ قابل استفاده در عرض 360px
- label و focus management صحیح
- عملیات اصلی با صفحه‌کلید
