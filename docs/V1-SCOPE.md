# محدوده قطعی Vetra Gantt 1.0.0

وضعیت: مصوب برای اجرا  
تاریخ تصویب: ۱۴۰۵/۰۶/۲۹ (2026-09-20)  
هدف انتشار: پایلوت محدود روی WordPress تک‌سایتی و هاست اشتراکی

## 1. هدف محصول

Vetra Gantt یک افزونه مستقل وردپرس برای تعریف پروژه، ساخت WBS، زمان‌بندی فعالیت‌ها با تقویم کاری، ثبت روابط و نمایش گانت و تقویم شمسی است. نسخه 1.0.0 باید بدون فراخوانی دستی REST و بدون ابزار توسعه قابل استفاده باشد.

## 2. کاربران و نقش‌ها

| نقش | اختیار |
|---|---|
| مالک پروژه | مشاهده و ویرایش پروژه‌ها و فعالیت‌های متعلق به خود |
| مدیر سایت (`manage_options`) | مشاهده و مدیریت همه پروژه‌ها |
| کاربر دارای `edit_posts` | ایجاد پروژه و مدیریت پروژه‌های متعلق به خود |
| سایر کاربران و مهمان | بدون دسترسی |

مالکیت در نسخه 1.0.0 بر اساس `created_by` است. اشتراک پروژه با چند کاربر و نقش اختصاصی پروژه خارج از محدوده این نسخه است.

## 3. محدوده الزامی نسخه 1.0.0

### 3.1 مدیریت پروژه

- صفحه «وترا گانت» در پیشخوان وردپرس
- فهرست پروژه‌های مجاز برای کاربر جاری
- ایجاد پروژه با عنوان و تاریخ شروع شمسی
- ویرایش عنوان، تاریخ شروع و تقویم کاری
- حذف پروژه با تأیید صریح و نمایش اثر حذف
- دریافت shortcode آماده کپی برای هر پروژه

### 3.2 تقویم کاری

- انتخاب روزهای کاری هفته
- جمعه به‌عنوان تعطیل پیش‌فرض
- افزودن و حذف تعطیلات موردی با ورودی شمسی
- ذخیره تاریخ‌ها به‌صورت ISO میلادی
- جلوگیری از ذخیره تقویم بدون هیچ روز کاری

### 3.3 WBS و فعالیت‌ها

- ایجاد، ویرایش و حذف فعالیت، سرگروه و milestone
- تعیین سرگروه و نمایش سلسله‌مراتب
- تغییر ترتیب فعالیت‌ها با کنترل بالا/پایین
- تغییر سطح با کنترل تورفتگی/بیرون‌رفتگی
- تولید خودکار WBS پس از تغییر ساختار؛ امکان ورود دستی WBS در نسخه 1.0.0 حذف می‌شود
- جلوگیری از چرخه، سرگروه نامعتبر و حذف سرگروه دارای فرزند

### 3.4 زمان‌بندی

- حالت خودکار و دستی
- مدت بر حسب روز کاری و شامل روز شروع
- روابط FS، SS، FF و SF
- lag مثبت، صفر و منفی بر حسب روز کاری
- roll-up تاریخ، مدت و سهم سرگروه از فرزندان
- تشخیص چرخه وابستگی پیش از ثبت نهایی

### 3.5 نمایش و تعامل

- نمای گانت با مقیاس روز، هفته و ماه
- نمای تقویم شمسی فقط‌خواندنی
- رابط فارسی و RTL
- وضعیت روشن برای loading، success و error
- جلوگیری از ارسال تکراری فرم
- هشدار بستن فرم دارای تغییر ذخیره‌نشده
- استفاده قابل قبول با صفحه‌کلید و نمایشگر موبایل

### 3.6 خروجی و بهره‌برداری

- خروجی CSV از فهرست فعالیت‌ها با UTF-8 BOM برای سازگاری با Excel
- مستند نصب، ارتقا، backup و rollback
- ZIP نسخه‌دار و قابل نصب از پیشخوان وردپرس

## 4. خارج از محدوده نسخه 1.0.0

- منابع انسانی و ماشین‌آلات
- هزینه، بودجه و جریان نقدی
- baseline و مقایسه برنامه/واقعیت
- درصد پیشرفت واقعی و EVM
- مسیر بحرانی، شناوری و resource leveling
- چندتقویمی برای یک پروژه
- اشتراک پروژه با تیم و نقش اختصاصی پروژه
- اعلان، ایمیل و گردش تأیید
- import از MSP/Primavera/Excel
- WordPress Multisite
- API عمومی برای سامانه‌های ثالث

این موارد فقط پس از پایدار شدن نسخه 1.0.0 وارد برنامه نسخه‌های بعدی می‌شوند.

## 5. قواعد قطعی دامنه

1. هر پروژه دقیقاً یک مالک و یک تقویم کاری دارد.
2. همه کنترل‌های دسترسی باید در backend اجرا شوند؛ مخفی‌کردن کنترل UI کافی نیست.
3. هر فعالیت فقط به یک پروژه تعلق دارد و والد و پیش‌نیاز آن باید در همان پروژه باشند.
4. milestone مدت صفر و تاریخ شروع و پایان یکسان دارد.
5. فعالیت خودکار بدون تاریخ شروع، از تاریخ شروع پروژه یا محدودیت پیش‌نیاز محاسبه می‌شود.
6. فعالیت دستی باید شروع و پایان معتبر داشته باشد.
7. سرگروه دارای فرزند از تاریخ و وزن فرزندان محاسبه می‌شود.
8. ساختار WBS و شبکه وابستگی نباید چرخه داشته باشند.
9. حذف پروژه باید فعالیت‌ها و وابستگی‌های همان پروژه را اتمیک حذف کند.
10. ذخیره تاریخ در دیتابیس میلادی و نمایش/ورود کاربر شمسی است.

## 6. قرارداد معماری

معماری نسخه 1.0.0 یک modular monolith داخل WordPress است:

| ماژول | مالکیت |
|---|---|
| Database | schema، migration و queryهای پایه |
| Project Service | پروژه، مالکیت و تقویم کاری |
| Task Service | WBS، ترتیب، فعالیت و وابستگی |
| Scheduler | محاسبات خالص زمان‌بندی؛ مستقل از UI |
| REST API | احراز مجوز، اعتبارسنجی و قرارداد پاسخ |
| Admin UI | مدیریت پروژه در پیشخوان |
| Gantt UI | ویرایش فعالیت و نمایش گانت/تقویم |

منطق زمان‌بندی، مالکیت و اعتبارسنجی نباید به JavaScript واگذار شود. UI فقط ورودی را جمع‌آوری و پاسخ backend را نمایش می‌دهد.

## 7. قرارداد خطا

| وضعیت | کاربرد |
|---|---|
| 400 | ورودی یا JSON نامعتبر |
| 403 | کاربر فاقد مجوز |
| 404 | پروژه یا فعالیت ناموجود |
| 409 | چرخه، تعارض ساختاری یا ویرایش هم‌زمان |
| 500 | خطای غیرمنتظره ذخیره‌سازی |

پاسخ خطا باید دارای `code` و `message` قابل نمایش باشد و اطلاعات SQL یا مسیر سرور را افشا نکند.

## 8. معیار پذیرش نسخه 1.0.0

- تمام قابلیت‌های بخش 3 از UI قابل اجرا باشند.
- کاربر نتواند پروژه یا فعالیت کاربر دیگر را بخواند یا تغییر دهد.
- چرخه WBS و وابستگی ذخیره نشود.
- محاسبات تاریخ برای تعطیلی جمعه، تعطیلات موردی، lag و milestone درست باشند.
- پروژه حداقل 500 فعالیتی بدون خطای عملکردی قابل استفاده باشد.
- نصب تازه و ارتقا از نسخه 0.2.0 روی staging موفق باشد.
- هیچ نقص Critical یا High باز باقی نماند.
- backup و rollback عملاً آزمایش شده باشند.
- یک مدیر پروژه نتایج پایلوت را با نمونه مرجع تأیید کند.

## 9. تصمیم‌های معماری (ADR خلاصه)

### ADR-001: WordPress Modular Monolith

پذیرفته شد؛ برای هاست اشتراکی کم‌هزینه‌تر و ساده‌تر است. سرویس مستقل یا Node runtime اضافه نمی‌شود.

### ADR-002: تاریخ ISO در ذخیره‌سازی

پذیرفته شد؛ تبدیل شمسی در مرز UI انجام می‌شود و Scheduler فقط ISO میلادی دریافت می‌کند.

### ADR-003: مالکیت تک‌کاربره پروژه

پذیرفته شد؛ کنترل دسترسی نسخه 1.0.0 با `created_by` و اختیار مدیر سایت انجام می‌شود.

### ADR-004: WBS تولیدشده از ساختار

پذیرفته شد؛ WBS دستی باعث ناسازگاری با ترتیب و تورفتگی می‌شود، بنابراین در نسخه 1.0.0 از `parent_id` و `sort_order` تولید خواهد شد.

## 10. Definition of Done نسخه

کد، migration، تست خودکار، تست انسانی RTL/شمسی، مستندات، ZIP نسخه‌دار، نصب staging، backup و rollback باید همگی تکمیل و ثبت شوند. صرف کارکردن قابلیت در محیط توسعه به معنی Done نیست.
